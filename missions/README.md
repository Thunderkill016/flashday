# SWE work factory V1

Repository-local orchestration for long autonomous engineering missions
(issue #62). Goals: a mission must never lose state, never drift in
scope, and never falsely declare success — and a *fresh* session must be
able to resume it from disk alone.

Deliberately boring: one Node CLI (`scripts/swe.mjs`), Markdown + JSON
artifacts under `missions/`. No dashboard, no database, no framework.

## Lifecycle

```
QUEUED ──swe:start──▶ RUNNING ──swe:verify──▶ VERIFYING ──(auto)──▶ RUNNING
                       │  │                                      │
                       │  └──swe:checkpoint --blocked──▶ BLOCKED ──┤
                       │            (swe:resume unblocks)          │
                       └──swe:finish──▶ DONE ◀── requires green verify on HEAD
                       └──swe:finish --result failed──▶ FAILED
```

V1 allows **one non-terminal mission at a time**. The queue is simply
mission directories without `state.json` — new missions are authored by
committing `missions/<id>/mission.md`; nothing generates them.

## Commands

```bash
npm run swe:status                  # all missions: status, cps, last verify
npm run swe:status -- <id>          # detail
npm run swe:start                   # start the only queued mission (or pass <id>)
npm run swe:checkpoint -- <id> --file cp.md           # record a checkpoint
npm run swe:checkpoint -- <id> --file cp.md --blocked # checkpoint + BLOCKED
npm run swe:verify -- <id>          # run the mission's required checks
npm run swe:finish -- <id>                      # DONE (needs green verify on HEAD)
npm run swe:finish -- <id> --result failed      # FAILED + report
npm run swe:finish -- <id> --summary notes.md   # append narrative to report
npm run swe:resume                  # context packet for a fresh session
```

## File layout

```
missions/
  TEMPLATE.md               copy this to start a mission
  <id>/
    mission.md              immutable definition (JSON frontmatter + sections)
    state.json              status, SHAs, checkpoints, verify runs, commands
    checkpoints/NNN-checkpoint.md   stamped, compact, resumable
    logs/verify-*.log       full output of every verification command
    REPORT.md               generated by swe:finish
```

## Mission file

`mission.md` = JSON frontmatter + narrative sections (see TEMPLATE.md).
Frontmatter fields: `id`, `objective`, `verification` (required array),
`browserVerification` (optional).

**Verification is allowlisted** — the only runnable shapes are
`npm run <script>`, `node tests/<file>.mjs|.js`, `node scripts/<file>.mjs|.js`
against files/scripts that exist. A mission can never smuggle arbitrary
shell into `swe:verify`.

## Checkpoints

The agent writes a compact Markdown file with ALL of these sections
(enforced): MISSION OBJECTIVE · CURRENT STATE · PROVEN FACTS ·
CHANGES MADE · CURRENT TEST STATUS · CURRENT HYPOTHESIS · OPEN PROBLEMS ·
IMPORTANT FILES · NEXT EXACT ACTION · CURRENT SHA.

`swe:checkpoint` stamps mechanical fields on top (checkpoint #,
timestamp, real git SHA, commits since start, dirty files) and stores it
under `checkpoints/`. Write checkpoints *before* risky steps and after
each semantic milestone — they are the resume payload, not a diary.

## Resume contract

`swe:resume` prints everything a fresh session needs: objective,
SHAs, commits since start, verification status, warnings (died mid-verify,
HEAD drifted, dirty tree), then the *full latest checkpoint*. State is
reconstructed from mission definition + latest checkpoint + git — never
from conversation memory.

## Safety (fail closed)

- `swe:start` refuses when: another mission is non-terminal; any tracked
  file is modified; any untracked file exists outside `missions/` and
  `node_modules`.
- `swe:finish` refuses DONE unless the last `swe:verify` was green **and**
  ran on the current HEAD (a commit after verify forces re-verification).
- Status `VERIFYING` left on disk means the process was killed mid-check —
  `swe:resume` surfaces it; re-run `swe:verify`.
- The CLI never runs force-push, reset, deploys, or anything outside the
  allowlisted verification shapes. ChatGPT-via-Playwright consults are
  advisory only — never paste secrets, tokens, or learner data, and
  validate significant advice against code/tests before applying.

## Testing

`tests/swe-factory.test.mjs` exercises the whole lifecycle in a
throwaway git repo (`SWE_REPO`/`SWE_HOME` env overrides): start safety,
checkpoint validation, verify gating, finish rules, blocked/resume.
